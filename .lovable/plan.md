# ABILITY360 — Functional, UI/UX and Security Hardening

Scope: fix the misleading duplicate sign-up flow, make the public pages reflect who is signed in, add real HTTP security headers, and tighten input validation — reusing the existing design, components and accounts system.

## 1. Duplicate registration

Today sign-up always shows "we've sent a confirmation link", even when the email already has an account, because the accounts service deliberately hides that fact.

- Add a server-side check (`src/lib/auth.functions.ts`) that looks up whether the email already has an account, running with server-only privileges — never in the browser.
- Protect it: strict email validation, length cap, normalisation (trim + lowercase), and a simple per-IP/per-email cooldown so it cannot be used to harvest addresses at speed.
- The sign-up form calls it before creating the account. If the email exists, no account request is sent and no confirmation-email claim is made.
- Show the result in a dialog built from the existing dialog component: heading "This email is already registered", body "Please sign in instead", primary "Sign in" button that goes to the sign-in page, secondary "Use a different email" that closes and refocuses the email field.
- Accessibility: focus moves into the dialog, Escape closes it, focus returns to the email field, labelled for screen readers, full-width buttons on small screens.
- Success wording only appears after the accounts service actually accepts the request; a failure shows "We couldn't send the confirmation email. Please try again."

## 2. Signed-in state on public pages

The top bar already switches between Sign in / Get started and Dashboard / Sign out. The home page still shows "Get started" links regardless (two places).

- Drive both home-page calls to action from the same session hook the top bar uses, so a signed-in visitor sees "Go to dashboard" instead of "Get started".
- Keep the check based on a verified session (the existing `useMe`, which re-validates with the accounts service), not a leftover local flag.
- Sign-out already cancels and clears cached data; extend the same treatment to an expired or invalid session: when the session check fails, cached data is dropped and protected pages send the visitor to sign-in.
- No stale signed-in UI: while the session is being confirmed the bar shows neither state, as it does now.

## 3. Security headers (enforced immediately)

Added in the server entry (`src/server.ts`) so they appear on every real HTTP response, not as page tags:

- `Content-Security-Policy` scoped to what the app actually loads: own origin, Google Fonts stylesheet + font files, the backend API and its realtime socket, the Google sign-in broker, images from own origin/data/blob and backend storage; `frame-ancestors 'self'`; `object-src 'none'`; `base-uri 'self'`; `form-action 'self'`.
- `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` disabling camera/microphone/geolocation/payment, and `Strict-Transport-Security` only on HTTPS responses.
- Known trade-off to be stated in the final report: the framework injects inline startup scripts and styles, so script/style rules need inline allowance for those. A nonce cannot be threaded through the framework's own injected tags without forking it. Everything else stays tightly restricted.
- After the change, every page is loaded and its response headers plus the browser console are checked so nothing legitimate is blocked.

## 4. Subresource integrity

The only external resource is the Google Fonts stylesheet, which is generated per browser and changes content, so a fixed integrity hash would break it. This will be documented as not applicable rather than faked. All other scripts and styles are bundled from this project.

## 5. Session storage in the browser

Requested: investigate moving session credentials out of browser storage into server-only cookies.

This will be delivered as a written investigation, not a rewrite in the same step, because the accounts client that stores the session is managed and regenerated by the platform, and replacing it touches every signed-in page, the server-side data access and the Google sign-in flow. The write-up will cover: what is stored today, which parts could move to server-only cookies, what would break, the cross-site request protection already in place, and a recommended path. Nothing is changed until you approve that path.

Meanwhile the practical exposure is reduced by the headers above plus the rendering and validation review below.

## 6. Unsafe rendering and input validation

- Sweep the code for unsafe HTML rendering. One known spot is the chart component's generated style block, which contains no user data; anything reachable by user input gets switched to safe rendering.
- Validation review across the forms (sign-up, sign-in, onboarding, applications, employer profile, competitions): trim and length caps on every free-text field, strict formats for email and phone, numeric-only for codes, sensible allow-lists for names without blocking legitimate ones.
- Re-check that the same rules are enforced on the server side — the database already restricts who can read and write each row; any field where only the browser validates gets a matching server-side rule.
- Paste stays enabled everywhere; password managers, autofill and assistive tech continue to work.

## 7. Rate limiting and account-flow abuse

- Confirm the hourly limit on account emails from the accounts service and record the effective figures.
- Apply the cooldown described in step 1 to the new email-check endpoint.
- Report which limits are enforced by the managed accounts service (sign-in attempts, confirmation-link expiry, token refresh and revocation) rather than duplicating them.

## 8. Verification

- Build and type-check clean.
- Automated browser run: sign up with a new email, sign up again with the same email (dialog appears, Sign in button navigates), sign in with valid and invalid credentials, confirm the home page and top bar change after sign in, sign out, then confirm a protected page bounces to sign-in.
- Response headers checked on the home page, sign-in page and a protected page.
- Console and network checked for anything blocked by the new rules.
- Final summary listing each finding as fixed, mitigated or not applicable, with the reasoning.
